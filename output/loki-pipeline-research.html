Task 01 / Define the contract and threading model

The source owns the call.

One goroutine can read, process and enqueue. It doesn’t need a dedicated pipeline worker. It does need an ordering and resource contract.

01 / EXECUTION

Call synchronously

No detached work before the acceptance boundary. Keep the source’s context.

02 / ORDER

One active call per stream

Within one source instance, prevent overlapping execution for identical original labels.

03 / LIMITS

Bound work and bytes

Limit active processing, decoded input and batches. Waiting goroutines still hold memory.

04 / COMMIT

Accept before acknowledging

Commit only resolved input. An ordered reader retries before moving to later batches.

05 / OWNERSHIP

Preserve retry input

Processing may mutate data. Retained data needs ownership or a clone.

06 / LIFECYCLE

Cancel, wait, then flush

Quiesce calls before replacing or stopping stages. Shared consumers remain concurrency-safe.

Illustrative pseudocode · not an implementation
Queue acceptance is not backend delivery. Buffered CRI / multiline needs a separate acknowledgement decision → task 05.

Task 03 / Check whether the contract is implementable everywhere
Execution is portable.
Delivery guarantees vary.
All source families can own pipeline execution. Some need serialization, bounded dispatch or a deliberate overload policy.
Feasible with adaptations

No / exclusive ownership
Use the reader directly

Yes / overlapping ownership
Coordinate before processing

Good upstream fit
Kafka & Pub/Sub
Sarama provides partition claim goroutines. Pub/Sub encourages synchronous callbacks and exposes message / byte flow control.
Acknowledge after acceptance. Kafka cancellation must also respect rebalance deadlines.

Request-level limits
HTTP sources
Admit requests before expensive decoding; cap input bytes and processing. HTTP/2 connection counts alone do not bound requests.
Use an explicit processing deadline. Response WriteTimeout is not a context deadline.
Go HTTP docs ↗

        
UDP inputs
Blocking the reader cannot slow a remote sender reliably. Finite queues eventually imply packet loss. Define drops and metrics for GELF and UDP syslog.
Kubernetes events
Informer callbacks run behind an unbounded notification buffer. A blocked callback can move congestion into that buffer. Another bounded queue does not fix this if it simply blocks the callback when full. Upstream implementation ↗
Cloudflare
Parallel time-range fetches emit the same labels. Serialize emission to prevent overlapping pipeline calls. If chronological range order is required, add ordered emission too; neither sharding nor a mutex sorts timestamps.

Task 05 / Identify the trade-offs we must make
Four decisions remain.
The scheduling choice is only one part of the reliability contract. These decisions determine whether removing the class actually simplifies the system.
Explicit decisions

        
01 · What does success mean for buffered stages?
The new CRI stage can return success while holding partial lines. Multiline also needs future input. Waiting for the final assembled record before reading more creates a circular wait:
Stage holds
a partial line
→
Reader waits
for final acceptance
→
Next line
cannot arrive
The missing input must come from the waiting reader.
Accept into the stage’s buffer
Simple synchronous API. Requires bounded buffers and draining. A crash can lose acknowledged partial records.
Separate submission from acknowledgement
Keep reading within a bounded window. Advance a contiguous commit position using completion receipts. Stronger semantics, more machinery.
Neither scheduler resolves this choice. CRI’s current behavior ↗

        
02 · How much ordering coordination do we retain?
Exclusive readers can run directly. Overlapping producers require coordination to preserve the proposal’s original-stream serialization.
Striped cancellable gates
Fixed memory, simple lifecycle and no workers. Unrelated streams can still collide and block each other.
Exact per-stream gates
Better isolation. Requires key identity, bounded registry management and safe cleanup.
A stage’s internal mutex protects state, but does not preserve order through the whole pipeline. Separate source instances and downstream label merges remain outside this guarantee.

        
03 · Is parallelism inside one input worth keeping?
One API request or one journal reader may carry many streams. Direct execution has only that caller’s processing capacity.
Keep the input sequential
Least scheduling machinery. A slow stream delays later streams in that input.
Add bounded source dispatch
Restores intra-input parallelism. Retains a dispatcher, workers or tasks, result aggregation and shutdown responsibilities.
Benchmark representative inputs before paying for this complexity. No production speedup was measured in this study.

        
04 · Where do limits and retry ownership live?
Each source needs an explicit active-work and memory budget. Shared downstream components see the sum of their sources’ concurrency.
Source owns admission and retry
HTTP limits before decoding; file batches stay bounded; broker messages remain unacknowledged until accepted. Reuse shared helpers.
State the remaining limits
Retries after partial fan-out can duplicate entries. A queue acknowledgement does not prevent loss on crash, exhausted send retries or drain timeout.
Both designs need cancelled calls to finish before data reuse, and need explicit overload behavior for non-replayable inputs.

        
The acknowledgement issue applies whether or not ShardingConsumer survives.

      


      

        
Task 06 / Make a decision suggestion
Adopt caller execution.
Make deletion conditional.
The evidence supports removing the mandatory sharding layer. It does not support replacing every source with uncoordinated direct calls.
Recommendation

        
Proposed direction
Reuse natural readers.
Share coordination for the exceptions.
Sources own their concurrency, contexts and acknowledgements. A shared cancellable serialization helper handles overlapping streams without adding worker goroutines.

        
Remove from the default path
  • A worker handoff for every file or container batch.
  • A mandatory fixed hash partition for all sources.
  • Worker lifecycle where a reader already owns the sequence.
Keep as explicit responsibilities
  • Per-stream serialization and source admission limits.
  • Write’s endpoint queues and HTTP sender workers.
  • Bounded dispatch only where intra-input parallelism is required.

        
Start with a file-source prototype
Direct calls, bounded batches, retained retry input and acknowledged offsets. Exercise full queues, cancellation, rotation and target replacement.
Cover the multiplexed sources
Test overlapping HTTP streams, partition label collisions, Pub/Sub callbacks and Cloudflare emission. Share ordering helpers instead of cloning logic into each source.
Resolve buffering, then measure
Choose CRI / multiline acknowledgement semantics. Compare representative throughput, allocations, tail latency and congestion behavior before removing useful intra-input parallelism.

        
Deletion gate: every source has a documented concurrency and ordering policy; buffered-stage acceptance is explicit; focused correctness checks pass; representative workloads justify the remaining scheduling choices.
